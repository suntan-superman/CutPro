# ADR 0002: Direct browser uploads with private quarantine

Status: Implemented locally; additive live migration and end-to-end certification required before push/deployment.

## Why

CutPro permits six photographs at 8 MiB each. Netlify's buffered function request limit can reject even one modern-phone image before Next.js validation or Sharp compression runs. Increasing platform limits, reducing the photo count, or making a bucket anonymously writable is not the solution. Keep the existing GitHub repository, Netlify site, Next.js application, and Supabase project. [Netlify function limits](https://docs.netlify.com/build/functions/configuration/).

## Data paths

```text
Browser -- small JSON --> CutPro authorization + durable upload draft
Browser -- image PUT --> Supabase private staging object (exact-path grant)
Browser -- small JSON --> CutPro per-file verification
                          |-- fetch one bounded staged image from Supabase
                          |-- gallery: trusted Sharp -> public normalized WebP
                          `-- estimate: validate -> Storage-side private copy
Browser -- small JSON --> atomic database finalization -> gallery rows / one lead
```

No browser-to-Netlify request or Netlify-to-browser response contains image bytes. Verification does fetch one image into the existing server runtime: this is bounded processing, not an incoming multipart gateway payload. It still consumes function memory/time and Storage bandwidth, so live phone-photo timing remains a release check. Six files are processed through separate sequential requests, not a single six-image function invocation. Fetch operations have timeouts, Sharp processing has a timeout and 60-million-pixel decoder cap, and bucket/object checks enforce 8 MiB. No new paid image service or second deployment architecture is introduced.

## Ownership and authorization

- All three gallery upload endpoints independently verify the Supabase user and `admin_users` membership. The draft is bound to that administrator; possession of its upload capability does not bypass admin authorization.
- An estimate starts only after normalized form validation, honeypot/minimum-fill-time checks, optional configured Turnstile, and a durable per-IP issuance budget. IP budget keys are HMAC digests, not stored raw addresses. Existing lightweight request throttles remain too.
- The browser generates a cryptographically random UUID request ID and two-UUID capability, retained in component memory for retries. The server creates the controlled draft and stores only the capability's SHA-256 hash. A UUID or arbitrary object path alone never authorizes finalization.
- Each draft records its complete, validated manifest of zero-to-six estimate files or one-to-six gallery files. Names are sanitized for display only. Random object paths are generated by the server and recorded before any grant or output object is created.
- Grants are issued for the exact temporary path, with `upsert:false`; they cannot overwrite or select a different destination. Bucket MIME restrictions and size caps are additional controls, not content-validation substitutes. Browser clients receive no service key and no database/Storage write policy.
- Verification accepts a session capability and file ID, never a caller-selected bucket or storage path. It checks actual Storage size, exact authorized size, magic bytes, and supported decoder/container structure. Finalization builds references exclusively from this private ledger.
- RPCs are service-role-only, security-invoker functions with fixed search paths. Ledgers have RLS and revoked public/anon/authenticated table permissions. A transaction locks the draft, verifies ready-file ownership/count, creates the complete gallery batch or exactly one lead, and caches the result in that same transaction.

## Image handling

`gallery-staging` is private. Raw gallery images cannot become public through a signed upload. Only trusted Sharp output enters `gallery-media`: rotation applied, maximum 2,200-pixel edge, WebP quality 84, metadata stripped. Categories, featured state, ordering, publish/unpublish, pairing, and deletion continue using existing gallery records. A normalized unpublished object's known URL remains public; unpublished is presentation state, not confidentiality.

`lead-photos` remains private. Source objects use `staging/<session>/<file>.<type>`; accepted originals are copied inside Storage to `<session>/<file>.<type>`. JPG/PNG/WebP pass a decoder check; HEIC/HEIF have signature and bounded ISO-BMFF box checks, but no promise of decoding unsupported codecs. Originals can retain GPS/EXIF and are accessible only through the existing authenticated admin signed-link mechanism. No WebP conversion is required for private reliability.

## Expiry, retries, and cleanup

The standard Supabase signed-upload API has a fixed **two-hour** grant lifetime; there is no supported custom `expiresIn` parameter. The CutPro draft expires after **30 minutes**. Those are different security boundaries, and a shorter draft does not revoke an already issued Storage grant. TUS is not used because its resumable-upload lifetime would need additional cleanup handling. [Supabase signed-upload contract](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl).

Keep temporary originals in place, immutable, until the grant lifetime plus a ten-minute margin ends. Removing them earlier would allow a still-valid grant to recreate the same object. The ledger remains authoritative through cleanup; already completed sessions preserve their accepted destination objects. Unfinished sessions lose both temporary and pre-recorded uncommitted destinations. No bucket-wide enumeration or deletion is used.

The existing site's `cleanup-uploads` scheduled function sweeps hourly, with bounded work and retriable failures. In normal operation cleanup occurs 130–190 minutes after initialization; outages or backlog can delay it. Logs expose counts only and warn of unfinished backlog. Scheduled functions are not publicly invocable in production and execute on published deploys, not ordinary local development. Use the dry-run-first CLI locally. [Netlify scheduled functions](https://docs.netlify.com/build/functions/scheduled-functions/).

Processing and cleanup use compare-and-set claims. A worker abandoned for ten minutes can be recovered; finalize requires an unexpired draft and matching claim. Existing results remain replayable after draft expiry and cleanup, without another insert or notification. Cleanup clears expired signed grants and draft PII from the ledger; retained finalized rows/photos follow the separate customer retention policy. Partial validation failure never inserts a partial gallery batch or a lead lacking its requested photos; tracked uncommitted outputs await cleanup.

## Rollout gates

Apply `supabase/migrations/20260921_direct_uploads.sql` to the existing project after the base schema. Do not reinstall the base schema or add permissive policies. Run lint, unit/real-PostgreSQL transaction tests, build, and `npm run check`. Then run the complete live authentication/gallery/testimonial/estimate/privacy/cleanup matrix, including encoded images over the former Netlify binary request budget. Only after local certification passes may changes be committed/pushed and verified on the existing Netlify site. Verify its scheduled function and large-photo timing too; no DNS changes.
